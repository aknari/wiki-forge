# WikiForge

**Author:** [T. Bautista](https://github.com/aknari)

Distil your raw notes into an interconnected wiki and query it with any LLM (Google Gemini, OpenRouter, LM Studio, Ollama...).

WikiForge turns the notes you actually write (one or more source folders — `00-src`, `01-inbox`… — plus `10-journal` if you want) into a distilled, cross-linked knowledge base in `20-wiki/`, and lets you ask questions about that wiki in plain language. It is a full TypeScript port of an earlier Python workflow — no Python is executed, everything runs inside Obsidian (desktop and mobile).

## Features

- **Sync wiki** — scans your sources and processes only new or modified notes (incremental, tracked by mtime in `80-support/.wiki-sync-state.json`). A cancellable progress modal shows the current file. A note is recorded as done only once a wiki page came out of it: an answer that carries no `FILE:`/`CONTENT:` block (a small model, or a prompt cut short by the context window) leaves the note pending, so the next run retries it instead of silently leaving it out of the wiki.
- **Process current note** — distils just the note you have open, on demand. A single notice stays on screen while it runs, naming the step (`analysing`, `merging`) and counting the seconds, and is replaced by the result — a slow model and a stuck one look nothing alike.
- **Smart synthesis** — two passes, and the second one only runs when it has something to merge into. The first writes the note out as a page and, in doing so, names the pages it belongs to; if none of those exists yet, that answer *is* the page — one model call. If they do exist, their content is read and a second pass merges the note into them, which is what makes a page accumulate instead of being rewritten from scratch on every run. Both answers come under an explicit **output contract** appended by the plugin (the editable rule files say *what* to write, the contract says *in what shape*): without it a model tends to answer in prose — or to quote the template back, which is why a quoted `FILE: [ruta] CONTENT: [texto]` never counts as a page. The merge may only rewrite pages that arrived in `CONTEXT`, i.e. pages that were read first. The instructions travel in the **system** message and the note in the user one, which is what makes a model process the note instead of answering "understood, please provide the content"; and an answer that arrives as a plain markdown document instead of blocks gets **one reformatting call** on its own text, which is where a small model can follow the shape where a description of the shape does not.
- **Deterministic index + log** — after a sync `20-wiki/index.md` is **rebuilt from the folder** (grouped by subfolder, each page with its own heading, its `tipo` and **its opening** — the first prose line of the body, markdown decoration out) and a timestamped entry is appended to `20-wiki/log.md`. Each entry carries the page's opening because a list of titles is not something a selection can be made from, and `query-rules.md` promises the index carries *summaries* of the pages: asked «¿Qué es Lisa?», `Modelado de CSRs en Lisa` reads like a page about one part — and it is the page that says RISC-V, so a selection by title drops it and the wiki answers that it does not know. The index used to be rewritten by the model on every sync, which is how it drifted from the folder — pages left out, links invented — and collected the model's leftovers on each pass; a directory listing cannot drift, cannot invent a name and costs nothing. The file is created if it is missing.
- **An ingest says when it added nothing** — the merge result is compared against the page it replaces, statement by statement, and a distillation that comes back with no new statement is said out loud — in `log.md`, in the notice, and under the note in the panel (`Ingested — nothing new`) — instead of being recorded as a success. **Measured on this vault**: the note that defines Lisa was distilled three times into `lisa-architecture-overview.md`, which came back **byte for byte as it was**, while the log said `Processed …`, the state marked the note as done and the panel kept offering the same suggestion. A statement counts as new when it resembles none of the ones the page had — on words *or* on letters, whichever matches better — because this model's documented letter noise (`dove-mode` for *Modo*, `Dispotcher` for *Dispatcher*) makes a line it re-rendered look like new content on words alone. Calibrated on the real pairs: a re-rendered line scores **0.80**, a fixed wording **1.00**, the sentence the wiki was missing **0.62** — hence **0.7**. The same comparison is what a merge has to pass to count as having distilled anything: on a merge that genuinely worked, the count came back at +19 and +18 statements on its pages.
- **Wiki check (report only)** — `Check wiki` measures the folder and writes a Markdown report: broken links (each with the most likely target, when there is one), pages the index does not list (a query never reaches those), index entries pointing nowhere, orphan pages, leftover blocks and pages whose `fuentes` do not resolve. Nothing but the report is written.
- **Mechanical cleanup** — `Clean wiki` previews the fixes that need no judgement — repair a broken link when a single plausible target exists, drop a leftover block — applies the ones you accept and rebuilds the index. Marker-looking blocks that *hold* information are reported and left alone, never deleted.
- **Ask the wiki…** — a chat-style modal: the model selects relevant pages from the index, reads them, and synthesizes an answer that ends with the *Fuentes* section the query rules ask for — the pages as wikilinks, so they are clickable. The selection is complemented **locally**: the pages whose own text mentions the question's words are read as well (the same ranking the source search uses, capped at three), because that selection is a model call at temperature 0.2 and measured on this vault it is a draw — three runs of the same question read five, five and **two** pages, and the two-page run is the one that answered that the wiki did not know what Lisa was. The panel therefore says **how much of the wiki answered** — `This answer was built from 2 of the 7 wiki pages` — so a short read is visible instead of passing as a complete answer. If the wiki has nothing, it falls back to scanning your tasks/journal/sources and suggests candidate notes — names of notes, it does not answer from the fallback. **Which notes it suggests is decided locally, by the words of the question, over the whole source set.** It used to take the fifteen newest notes of each area, and on the vault this was written for that covered at most 45 of 179 notes: the note that actually answered the question sat at position **44 of 101** and was never offered, so the panel reported "no answer" about a vault that held it. The model is still asked which of the candidates holds the answer, but the *finding* no longer depends on it. The panel also says **how much it looked at** — `12 of the 178 source notes mention “lisa”; the 20 best were offered to the model (11% of the sources)` — because a search over a fifth of your notes and one over all of them look identical on screen and mean opposite things. The model's answer is **matched back onto the list of paths it was given**, so a bare file name (`Notas sobre Lisa.md`) still resolves to the note it means (`00-src/30-dev/30-lisa/Notas sobre Lisa.md`) — and an answer that matches nothing is dropped rather than shown as a row that cannot be opened. The matching compares **file names on both sides**, so a name carrying a folder the list does not have resolves as well: the pool names wiki pages relative to the wiki folder, and a model shown a wiki path in the rules answers `20-wiki/04-lisa/lisa-architecture-overview.md` for `04-lisa/lisa-architecture-overview.md`. A reply that is a plain list of names instead of a JSON array is read rather than refused (whatever it names is still resolved against the pages that exist, and a line naming nothing is dropped). Both of those cost a whole answer when they were not handled: the context came out empty and the panel reported that the wiki had no answer while the index was listing the pages that held it. Each suggestion is a link that opens the note, and comes with an **Ingest** button that distils it into the wiki in one click so the question can be asked again; a note that cannot be ingested (the journal while *Include journal in sync* is off, or anything inside an excluded folder) says why instead of offering the button. While a call runs the panel counts the seconds it has been waiting (`Thinking… 12s`, `Ingesting… 34s`), and an ingest that fails says so **under that note** with the provider's own message and leaves the button usable — it never reports a failure as a success. **Ask** and **Save to note** share one row at the top, above the answer — the save button used to be the last element of the panel, and an answer that ends with its own *Fuentes* section (which `query-rules.md` asks for) makes the panel look finished right there, so it was there and went unseen. The panel does not add a *Sources* list of its own under the answer: the rules already require the answer to end with one, so it was the same information twice, and only one of the two copies was clickable — the answer's is wikilinks, the panel's was plain text. That *Fuentes* list is moreover **reconciled with the pages that exist** before anyone reads it, because a model writing links from memory gets names wrong and `lisa-rchitecture-overview.md` looks like a link while leading nowhere. Each name is resolved by title key (so a bare name, one with folders in front and one carrying its `.md` are one thing, which is how Obsidian resolves a link as well), then by the same one-typo, unambiguous-only rule *Check wiki* uses to suggest a repair — a link saved today is a link `Clean wiki` would have repaired tomorrow, same policy, earlier. What counts as a citation is decided by **shape**, not by a trailing `.md`: a path (`20-wiki/04-lisa/lisa-trap-management`), a name with an extension and a slug (`lisa-trap-management`) are all reconciled, and a phrase is left alone as prose. It used to require the extension, so a list written without it fell through every branch — not a link, so not repaired; not a `.md` name, so not reported either — and the answer shipped with a citation naming a page that does not exist while the panel said nothing. The repair is applied to the **file name**, so a typo behind a folder path is repaired too (comparing a whole path against bare names can never succeed: the folder words are dozens of edits of noise). And when a name *is* repaired, it is shown with the page's own name rather than the typo — leaving `lis-rchitecture-overview` on screen next to a working link leaves the repair half done. The link *text* is never rewritten (an alias is the author's wording) and a line that is only a file name becomes the link it was trying to be. A name that matches no page is **left exactly as written** — nothing is invented — and the panel says so under the answer, naming the citations that lead nowhere and noting that *Check wiki* keeps reporting them in the saved page. That button is put in place **before** the answer is rendered: `MarkdownRenderer.render` appends the text to the DOM and *then* returns a promise that can fail (embeds, post-processors), and with it after that await a failing render left the panel showing the answer and nothing else — an unhandled rejection, because the caller did not await the method. So it is set up first, the answer is rendered with a real `sourcePath` (a post-processor from another plugin may look the note up by it, and `''` is not a note), and a render that reports a failure **keeps what it drew** — the promise covers every plugin's post-processor, so a rejection can mean someone else crashed while the answer is already on screen — falling back to plain text only when nothing was drawn, and logging the reason. Answers can be saved with **Save to note** to a file in the *Queries folder* (`YYYY-MM-DD-HHMM.md`, named after the minute, with the question as its `#` title and `question`/`date`/`fuentes` frontmatter). The note does not repeat the list in its body either: `fuentes` carries it, and the answer already closes with its own *Fuentes* section, so a second list was the same thing a third time. An answer that read no page declares `fuentes: []`. Saving also **rebuilds the index**, so the answer is reachable by the next query right away. If your queries folder points *inside* the wiki (`20-wiki/queries` by default in older setups, `10-journal/queries` now) the saved answers become wiki pages: they are listed in the index and measured by *Check wiki*. They are **not read as sources**, and that is deliberate. An answer is derived from the distilled pages, so feeding one back into a new answer lets a stale answer — an error in it included — cite itself: asking the same question again puts a page titled exactly like the question in front of the selection phase, and the answer written yesterday, *before* the pages it came from were corrected, would come back as a source today. The pool the selection phase may read therefore leaves the answers out; the index still lists them, so they stay findable and auditable, and `query-rules.md` states the policy as well. Nothing is remembered between questions either — index, selection and reads are all taken fresh on every ask, so a question asked again after ingesting a new source is answered from the new pages. The reason to keep the folder inside the wiki is that the answers enrich it as pages: a record of what was asked and how it was answered. Two concrete things a saved answer is for, since it is easy to look at it and see no use: it is the **only copy left once the panel closes** (the modal's text is gone with the modal), and `fuentes` is the one list of sources that **cannot be wrong**, because the plugin writes it from the files it actually opened rather than from the model's wording — which makes it the note to compare against when the wiki changes: ask the same question after ingesting a source and you have written before and after. What a saved answer is *not* is knowledge: it does not feed the next answers (that is the paragraph above), so an answer worth keeping as knowledge belongs in a note of yours under the sources, distilled from there like any other. Move it outside only if you want the wiki strictly distilled from your notes.

The **ingest** is kept out of that folder too, in the three places it could reach it: the answers section is missing from the map the ingest is shown (a note can read a page titled like its own subject as the place to put it — an answer is not a page a note distils into), an answer is never read as merge context, and a block that names one anyway is **dropped and logged** instead of being written over the answer. The index still lists them for you; the distiller simply cannot see them.
- **Search the sources (local, no model)** — the other half of a question. *Ask* answers "is this in the wiki?"; this answers "where in my notes is this at all?", and it is the one that works when the model does not: no key, no quota, no server, nothing to wait for. It scores **every** source note against the words of the question and shows the best twenty, each with **which words made it a candidate**. Name matches weigh more than body mentions (a title containing the word is almost always about it), repeats inside one note stop counting past a cap (so a long note cannot bury the list by repeating itself), and matching starts at word boundaries, so `lisa` matches `Lisa` and `lisas` but not `analisa`. Folding strips combining accents only and the word split is by Unicode letter class, so a question in Tifinagh (`ⵜⴰⵎⴰⵣⵉⵖⵜ`), Greek or Cyrillic keeps its terms — a split written for ASCII turns those into zero terms, which then looks exactly like an empty vault. A question with no distinctive word (`¿qué es?`) is not a search at all, and says so instead of pretending.
- **Several source folders** — the notes to distil can come from more than one root (`00-src`, `01-inbox`…), with the exclusion list applied inside each of them. Update from an earlier version: an existing single `srcDir` is read as a one-folder list, so nothing is lost.
- **Any LLM provider** — Google Gemini (REST) or any OpenAI-compatible endpoint (OpenRouter, LM Studio, Ollama, llama.cpp, NVIDIA NIM...). A base URL on this machine or the local network **needs no API key**: the address is recognised, the key requirement is dropped, and no `Authorization` header is sent (a key you *do* store is still sent, so a private server that authenticates is unaffected). In settings you pick the **model from a dropdown** filled with the provider's own list of *chat* models, with the **free-tier ones first** (a label you keep up to date, since Google does not publish tiers through its API); anything missing can be typed by hand.
- **Faithful by default, not creative** — every call goes out at **temperature 0.2**, on both the Gemini and the OpenAI-compatible route. The plugin used to send no temperature at all, which leaves the choice to whatever default the provider has; on a local model that came back as letter-level noise in a paraphrased answer (`Dispotcher` for *Dispatcher*, `pora` for *para*, `sintencia` for *síntesis*, a source cited as `lisa-rchitecture-overview.md`) while the same model's distillation of those same pages came out clean. The content was right in every case, which is the point: each call this plugin makes is a *reading* task, and a low temperature keeps the answer on the wording of your notes.
- **Only models that can chat** — the dropdown is filled from the provider's own list, and two different filters are applied to it. Models the provider says cannot chat are dropped for good (Gemini via `supportedGenerationMethods`, Groq via `output_modalities`, which is what marks its Whisper and speech models); then your editable *Hide models* patterns remove the rest you do not want to see (test classifiers and the like), because a guard model is text-in/text-out and no field distinguishes it. Editing the patterns needs no extra request: they are applied when the list is drawn, and the number hidden is shown next to the dropdown.
- **Secure API key** — the key is stored in the **system keychain** via Obsidian's secret storage (`app.secretStorage` on 1.11.4+, falling back to `Plugin.setSecret/getSecret`). It never lives in `data.json` or any vault file.

  It is stored under the id `wiki-forge-api-key`. Obsidian only accepts ids of lowercase letters, numbers and dashes (`/^[a-z0-9-]+$/`, 64 characters max), which is why the id is not camelCase: an earlier version used `wikiForgeApiKey`, Obsidian's `setSecret` refused it with *"Secret ID is invalid"*, and the key was never saved. A key left under that old id is still read on start-up and is moved to the valid one automatically. You can see and edit the stored secret in Obsidian's own **Secret storage** settings.
- **Live rule files** — the distiller and query rules are Markdown files in your vault (`forge-rules.md`, `query-rules.md`, both configurable paths), created with embedded defaults on first load. Edit them without touching code. An existing `forge-rules.md` is never overwritten, so an update keeps your wording: the shipped default no longer asks for a fixed number of links per page (a quota the model filled by inventing page names that did not exist), and if yours still has one, removing that line is what stops the broken links at the source.

## Requirements

- Obsidian 1.11.4 or newer.
- An API key for the provider you choose (Gemini key, OpenRouter key, or **none** for a local server: LM Studio, Ollama, llama.cpp…).

## Installation

See **[INSTALL.md](INSTALL.md)** for the release, source and BRAT paths, and for what the plugin writes into your vault.

**Manual install (no build needed):**

1. Create the folder `.obsidian/plugins/wiki-forge/` inside your vault.
2. Copy `main.js`, `manifest.json` and `styles.css` from the release into that folder.
3. In Obsidian: **Settings → Community plugins**, make sure Restricted mode is off, and enable **WikiForge** in the *Installed* tab.

**From source:**

```bash
npm install
npm run build   # compiles into dist/
npm run deploy  # build, then copy dist/ into .obsidian/plugins/wiki-forge/
```

## Configuration

Open **Settings → WikiForge**:

| Setting | Default | Description |
|---|---|---|
| Queries folder | `10-journal/queries` | Where *Save to note* writes an answer. Point it inside the wiki folder and the answers become wiki pages (listed, measured, reusable as context); the index is rebuilt on every save either way. |
| Provider | `google` | `google` = Gemini directly; `openai` = any OpenAI-compatible API. |
| Base URL | `https://openrouter.ai/api/v1` | Shown only for the OpenAI-compatible provider — Gemini has a fixed address. For local servers: `http://localhost:1234/v1` (LM Studio), `http://localhost:11434/v1` (Ollama). |
| Model | `gemini-2.5-flash` | Dropdown with the provider's **chat** models (**Fetch models**), free-tier names first and always including the current one; **Write a model name…** for anything not listed. The fetched list belongs to one provider *and* base URL: change either and it is discarded, with the saved model shown as *from another provider* until you pick one from the new list. |
| Free-tier name patterns | `flash`, `!tts`, `!image` | Label only, Gemini only: Google does not expose the billing tier, so a model whose name contains one of these (one per line) is shown as *free tier* — the Pro models left the free tier in April 2026. A line starting with `!` is an exclusion and wins over the inclusions. Empty the list to stop labelling. |
| Hide models | `whisper`, `tts`, `orpheus`, `embed`, `rerank`, `guard` | One pattern per line: a model whose name contains one is left out of the dropdown. It covers what the provider's metadata cannot say — a guard classifier is text-in/text-out like any chat model. `!` brings a model back (`!safeguard`). The model you have selected is never hidden. |
| API key | — | Password field + **Save & test** (stores it in the system keychain *and* proves it works by fetching the model list) + **Clear**. The two are reported separately, so "the key could not be stored" never reads as "the provider rejected the key". Not required when the Base URL is local (`127.0.0.1`, `localhost`, `::1`, `*.local` or a private `10.`/`192.168.`/`172.16-31.` address) — the field says so instead of asking for something a local server cannot give. |
| Sources folders | `00-src` | One folder per line: every one of them is scanned as a source root (`00-src`, `01-inbox`…). |
| Folders & files | `10-journal`, `20-wiki`, `80-support`, … | All journal/wiki/rule paths, fully configurable. |
| Excluded subdirectories | the usual list | One folder name per line; skipped inside *each* source folder. |
| Include journal in sync | off | Also ingest `10-journal/` during *Sync wiki*. |
| Save answers to note | on | Show the *Save to note* button next to **Ask**, once there is an answer to save. |
| Report path | `80-support/wiki-forge/informe.md` | Where *Check wiki* writes its report. Keep it outside the wiki folder, so the report is not itself measured as a page. |
| Check after sync | on | Refresh the report after every *Sync wiki*. Read-only, so it cannot damage anything. |

**Limits and what a failure says.** One distillation carries a note of up to **200 KB** (the merge prompt sends the note whole); a bigger one is refused with its size in the message and nothing is written, rather than silently distilled from a truncated copy. When a model call fails, the message carries the size of the request, how long it waited and the model, and a transport failure (`net::ERR_CONNECTION_CLOSED` and friends — the connection died before the provider answered) names what usually causes it, because that error otherwise says nothing and is rarely the plugin's doing. A **quota refusal (429)** is reported with the provider's own detail — *which* quota ran out and how long it asks you to wait. **How patient a call is then depends on the failure**, because one fixed pause cannot mean all of them: an overloaded model (`503`, “high demand”) is retried three times with growing pauses (5s, 20s, 45s), since that clears on its own; a per-minute quota waits what the provider asks for, capped at a minute; a cut connection gets one more try; and a `PerDay` quota or a refusal that will not change (a rejected key, a model that does not exist) is not retried at all — waiting there only delays the sentence. When every attempt dies after about the same span with no answer, the message says so and names it for what it is — a **timeout somewhere between Obsidian and the provider** (an HTTPS filter, a proxy, a VPN), not a refusal by the model. And when the failure is an overloaded model (`503`, “high demand”), the message says what actually helps: *that* model is the crowded one, so a different one from the list answers at once — an HTTPS filter that cuts silent connections is a different problem, and a filter that inspects traffic is worth adding an exclusion for. The per-day message also says the part nobody can read out of a quota id: *every model has its own*, so another free-tier model answers immediately.

**On a free tier, plan for it.** Each note costs two model calls (decide which pages to touch, then write them), so the free-tier request-per-day cap is roughly half as many notes as requests: a first sync of a large sources folder can take more than one day, and it does not fail — a *Sync wiki* that meets a quota refusal **stops there** instead of walking the rest of the folder, tells you how many pages it did write, and leaves the state untouched, so the next run picks up from the first note it did not reach. Processing a few notes at a time, or a local model (`LM Studio`, `Ollama`) for bulk work, is the practical way round it.

## Usage

| Command | What it does |
|---|---|
| `WikiForge: Sync wiki` | Process all new/modified source notes (progress modal, cancellable). |
| `WikiForge: Process current note` | Distil only the active note. |
| `WikiForge: Ask the wiki…` | Open the query modal (`Cmd/Ctrl+Enter` to send; *Save to note* stores the answer). |
| `WikiForge: Check wiki (report)` | Measure the wiki folder and write the report. Read-only. |
| `WikiForge: Clean wiki (mechanical fixes)` | Preview and apply the repairs that need no judgement, then rebuild the index. |
| `WikiForge: Forget current note (re-distil on the next sync)` | Drop the active note from the sync state, so the next sync distils it again. |
| `WikiForge: Reset the wiki…` | Preview and carry out a reset: delete the distilled pages, keep the saved answers, clear the sync state. |

The ribbon icon (sparkles) also opens the query modal.

## How it works

```
00-src/ (+ any other source folder)
  │  mtime diff
  ▼
draft prompt (rules + index + note) ──▶ FILE:/CONTENT:/---END---   the page, and its name
  │
  ├─ those pages do not exist yet ──▶ write them as new pages            1 model call
  │
  └─ they do exist ──▶ merge prompt (rules + index + those pages + note) ──▶ write   2 calls
  ▼
20-wiki/ · index.md rebuilt from the folder · log.md appended
```

Query flow: `20-wiki/index.md` → selection prompt + local keyword pass → read selected pages → synthesis answer (+ raw fallback over tasks/journal/sources).

## When the rules change, and starting over

The sync state (`<support dir>/.wiki-sync-state.json`) records which notes have been distilled — by `mtime` — and a fingerprint of the rules that were in force. Two consequences are worth knowing before they surprise you:

- **Editing the rules does not re-distil anything.** The pages written under the older rules stay exactly as they are, and until now nothing anywhere said so: the state compared `mtime` alone, so a note edited six months ago and a note distilled under a prompt you have since replaced looked identical. Now the fingerprint is compared on every sync, and a change is announced once and written to `log.md`.
- **Deleting a page is not enough if you go through the sync.** The state still counts the note as done, so a sync will not bring the page back, and the wiki stays incomplete while reporting itself up to date.

### Rebuilding one topic

Delete its pages by hand and run `WikiForge: Process current note` on its source note. That command always distils, whatever the state says — no reset needed. Deleting first turns it into a single draft call instead of a draft plus a merge, and a fresh draft is where the "state the subject" rule applies most directly. (`Forget current note` is for the other direction: when you want the sync, not a one-off command, to pick the note up again.)

Since 0.7.0 the merge pass is held to the same rule, so re-processing an already-distilled note is no longer a guaranteed no-op: if a page does not open by saying what its subject is, merging is required to write that sentence rather than only to append.

Since 0.9.0 the rule says what it means when it meets "do not duplicate": **a fact already stated on another page is not coverage**, so the page whose subject X is still opens by saying what X is, and the merge contract says so in as many words — "covered elsewhere" was the excuse a merge used to leave the opening as it was, with the identifying fact of the note sitting *unused* in its own `CONTEXT`.

### Starting the wiki from scratch

1. `WikiForge: Reset the wiki…` — it lists every page it would delete, keeps the saved answers unless you turn that off, deletes the rest, clears the state and rebuilds the index. The pages go to the Obsidian trash, so a reset is reversible by hand.
2. `WikiForge: Sync wiki` — every source note is pending again. This is the whole folder at two model calls a note, so the confirmation states the count before you commit: on a local model it is a job to start deliberately.

Both halves matter. Clearing the state without deleting the pages only merges the notes back into the pages that are already there, which cannot fix a wiki whose problem is what those pages say.
